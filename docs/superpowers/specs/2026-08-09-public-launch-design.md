# Design: taking kakeibo public

Date: 2026-08-09
Status: approved, ready for planning
Supersedes: the "no accounts or multi-tenancy" non-goal in `docs/kakeibo_spec.md` §3

## 1. What we are building and why

kakeibo today is a single-user local tool: one global session, no auth, a
Postgres ledger seeded with 352 synthetic transactions. This design takes it
public as a **playable portfolio piece** — a hosted site where a visitor can
talk to the agent against their own copy of a synthetic ledger within seconds of
landing, and where the engineering (the from-scratch loop, the guardrails, the
traces, the evals) is the thing on display.

It is explicitly not a finance product for managing real money. Importing your
own statement exists, works, and is deliberately secondary.

### Decisions taken (owner, 2026-08-09)

| Question | Decision |
| --- | --- |
| Purpose | Playable portfolio piece; everyone gets a synthetic ledger |
| Monthly Gemini spend | **Under $20/month**, hard ceiling with a global kill-switch |
| Entry experience | Anonymous try-it-now (no signup), account to persist |
| Bring-your-own-key | **No.** One code path; everyone uses the owner's key |
| Real statement upload | Allowed for everyone including anonymous, **auto-deleted after 24h** |
| Tenant isolation | Explicit `ownerId` scoping **plus** Postgres RLS as a backstop |
| Demo ledger provisioning | Lazy per-visitor clone on first ledger-needing request; anonymous expires in 24h |
| Confirm-before-write gate | Loop becomes **suspendable** (see §6) |
| Admin | Single-operator dashboard at `/admin`, allowlist by email (see §9) |

### Success criteria

1. A first-time visitor can ask the agent a real question about a real ledger
   without signing up, in under ten seconds from landing.
2. No visitor can ever observe another visitor's data. Proven by a test suite,
   not by inspection.
3. A month of traffic cannot cost the owner more than the configured ceiling,
   and hitting that ceiling degrades to something useful rather than an error.
4. `pnpm lint && pnpm typecheck && pnpm test` stay green, including the existing
   double-entry invariant and prompt-injection suites.
5. Nothing in CLAUDE.md is violated: no AI co-author trailers, money stays
   integer minor units, README numbers stay measured, no secrets in git, no
   agent framework in core.

## 2. Identity and tenancy

**Every visitor is a Better Auth user from their first request.** Anonymous
visitors are simply users who have not attached credentials yet, via Better
Auth's anonymous plugin. This collapses what would otherwise be two principal
types into one, and means `owner_id` on a ledger row is always `user.id`.

- Auth: Better Auth with the Drizzle adapter (`drizzleAdapter(db, { provider:
  'pg' })`), email/password and Google OAuth, tables generated by the Better
  Auth CLI alongside the existing Drizzle schema.
- Anonymous: the anonymous plugin issues a session with a synthetic email and
  an `isAnonymous` flag. No PII is captured.
- **Linking:** when an anonymous visitor signs in, the plugin's
  `onLinkAccount({ anonymousUser, newUser })` hook runs a single transaction
  repointing `owner_id` from `anonymousUser.id` to `newUser.id` across every
  owner-scoped table. The ledger does not move; only its owner changes. The
  plugin deletes the anonymous user row afterwards, which is why the ledger must
  be repointed inside that hook and not lazily.
- **Expiry:** a nightly job deletes anonymous users older than 24 hours;
  `on delete cascade` removes their ledger. Signing in clears the expiry by
  construction, because the row is no longer an anonymous user.

## 3. Data model changes

### 3.1 Owner column

Add `owner_id uuid not null references "user"(id) on delete cascade` to:

`accounts`, `transactions`, `postings`, `rules`, `budgets`, `memories`,
`import_batches`, `trace_runs`, `trace_events`.

Better Auth names its principal table `user`, which is a reserved word in
Postgres and must be quoted in every hand-written SQL statement (policies,
migrations, the reaper). If quoting proves noisy, rename it via the auth
config's `modelName` to `auth_user` and use that consistently.

`postings` and `trace_events` carry it **denormalised** rather than inheriting
through their parent. Two reasons: RLS policies are per-table and cannot follow
a join, and both tables are queried directly (postings by every report,
trace_events by the trace viewer). Correctness is maintained by the repository
layer, which is already the single insert path for both.

Index `(owner_id, ...)` as the leading column on the existing indexes.

### 3.2 Uniqueness change (breaking)

`accounts.name` is currently **globally unique**. It must become
`unique(owner_id, name)`. Left as-is, the second visitor to exist cannot have a
"Groceries" account and seeding their ledger fails.

`budgets` keeps `unique(account_id, month)` — `account_id` is already
owner-scoped transitively, so no change is needed.

### 3.3 New tables

```
conversations          id uuid pk, owner_id uuid fk, title text null,
                       created_at, updated_at

conversation_messages  id uuid pk, conversation_id uuid fk, owner_id uuid fk,
                       seq int, message jsonb
                       -- one CanonicalMessage per row, stored verbatim

suspended_turns        id uuid pk, conversation_id uuid fk, owner_id uuid fk,
                       history jsonb,          -- messages up to the tool request
                       completed_results jsonb,-- read-tier results already run
                       pending jsonb,          -- PendingConfirmation[]
                       usage jsonb,            -- tokens spent before suspending
                       cost_usd_est numeric(10,6),
                       created_at, expires_at

rate_limits            key text pk,            -- sha256(ip + daily_salt)
                       window_start date, count int
```

### 3.4 Additions to the Better Auth `user` table

Better Auth generates this table; two columns are added to it rather than kept
in a parallel table, because both are read on every authenticated request and a
join would be pure overhead:

- `blocked_at timestamptz null` — set by the operator action in §9.4.
- `is_anonymous boolean` — supplied by the anonymous plugin; relied on by the
  24-hour reaper and by quota selection.

### 3.5 Persistence notes

**`message` must be stored verbatim, including `providerMeta`.** Gemini 3.x
attaches an opaque `thoughtSignature` to `functionCall` parts, and replaying a
tool turn without it is a hard HTTP 400. A persistence layer that "cleans up"
the message shape will break resume in a way that only shows up on tool calls.

`rate_limits.key` is a salted hash so raw IP addresses are never stored. It is
the only new table that is NOT owner-scoped; `conversations`,
`conversation_messages` and `suspended_turns` carry `owner_id` and get the same
RLS policy as everything in §3.1.

## 4. Tenant isolation

Two independent mechanisms, because the failure mode — showing one visitor
another visitor's finances — is the worst thing this system can do.

### 4.1 Explicit scoping (application layer)

Every repository function takes `ownerId` as its first parameter. No implicit
context, no AsyncLocalStorage: an explicit parameter is visible at every call
site and trivially testable. Roughly 24 functions across
`packages/ledger/src/repo/` are affected.

### 4.2 Row-level security (database layer)

Every owner-scoped table gets:

```sql
alter table <t> enable row level security;
create policy <t>_owner on <t>
  using (owner_id = current_setting('app.owner_id')::uuid)
  with check (owner_id = current_setting('app.owner_id')::uuid);
```

A `withOwner(ownerId, fn)` helper opens a transaction, issues
`SET LOCAL app.owner_id = $1`, and runs the callback inside it. `SET LOCAL` is
required rather than `SET`: it is scoped to the transaction, so a pooled
connection handed to the next request cannot inherit the previous request's
owner. This is the specific thing that makes RLS safe behind Neon's pooler.

A forgotten `where owner_id = ...` therefore returns **zero rows** rather than
someone else's ledger — it fails closed.

Migrations, seeding and the eval harness connect as the table owner, which
bypasses RLS by default. The application connects as a separate, non-owning
role that does not.

## 5. Cost control

Measured inputs: a cached web chat turn costs **~$0.0045**; the median eval task
costs **$0.0106**. A $20/month ceiling is **$0.667/day ≈ 148 live turns/day**,
which is roughly **20–40 live visitors per day**. This is a real constraint and
the design accepts it rather than pretending otherwise.

Four layers, cheapest first:

1. **Per-owner daily quota** — 8 messages for anonymous, 25 for signed-in.
   Counted from `trace_runs` (which already records owner and cost).
2. **Per-IP daily cap** — 20 messages per salted-hash key per day, so clearing
   cookies to mint a fresh anonymous user does not reset the budget. The cap is
   deliberately higher than the 8-message anonymous quota rather than equal to
   it: offices, universities and mobile carriers put many genuine visitors
   behind one address, and a cap of 8 would let the first visitor lock out the
   rest.
3. **Global daily budget** — `sum(cost_usd_est) from trace_runs where started_at
   > current_date` against `GLOBAL_DAILY_BUDGET_USD` (default `0.667`). Tracing
   is already synchronous, so this number is exact and free to compute.
4. **Turnstile** on the anonymous "start chatting" action.

Model stays Flash tier for everyone (already the default `AGENT_MODEL`).

**Graceful degradation.** When any limit trips, `/api/chat` returns 503 with a
machine-readable `reason` (`owner_quota` | `ip_quota` | `daily_cap`) and the UI
falls back to the replayed-fixture demo with an honest banner. It never shows a
generic error. The fallback is free and unlimited because it replays recorded
`fixtures/` responses client-side — the same fixtures CI already uses.

## 6. The suspendable loop

### 6.1 Why

The current confirm gate has `/api/chat` block on an in-memory promise that
`/api/confirm` resolves. On Vercel these are two different function invocations
with no shared memory, so the gate cannot work as written. (Moving the store to
`globalThis` fixed the equivalent bug on a single long-running process; that fix
does not survive the move to serverless.)

### 6.2 Design

`runTurn` gains a suspend path, replacing the blocking `ConfirmFn` with a
policy:

- `'auto-allow'` — MCP with `ALLOW_WRITES=1`, eval tasks with `confirm: allow`
- `'auto-deny'` — eval tasks with `confirm: deny` or `none`
- `'suspend'` — the web

Under `'suspend'`, when the loop reaches step (g) and the batch contains
write-tier calls, it:

1. executes the **read-tier** calls in that batch normally,
2. returns `status: 'suspended'` with `pending: PendingConfirmation[]` and the
   completed read results,
3. does **not** append a tool-results message.

The caller persists history + completed results + pending into
`suspended_turns`, **including the usage and cost accumulated so far**. Without
that, the model calls made before the suspension are invisible to the resumed
turn's `trace_runs` row, and the global budget cap in §5 silently undercounts
every conversation that involved a confirmation — which is exactly the
conversations that cost the most. `suspended_turns` therefore also stores
`usage jsonb` and `cost_usd_est numeric`, and resume seeds its totals from
them. The client renders one confirmation card per pending write.
`POST /api/confirm` records decisions; a follow-up request resumes:

```ts
runTurn({ resume: { suspendedTurnId, decisions: [{ id, allowed }] }, ... })
```

Resume executes the approved writes, emits `User declined. Do not retry without
new instruction.` for the rest, assembles **all** results — reads from
persistence, writes from now — into a single tool-results message, and continues
the loop from step (h).

### 6.3 The parallel-calls subtlety

The provider requires the number of `functionResponse` parts to equal the number
of `functionCall` parts in the turn being answered. So the loop cannot suspend on
one write while answering another call in the same batch. **All** writes in a
batch suspend together and resume together, and read results from that batch are
persisted rather than re-run, so the data cannot shift between suspend and
resume.

Getting this wrong produces a hard 400 that only appears when the model happens
to emit a mixed batch — so it needs a test with a scripted adapter emitting
exactly that shape.

### 6.4 What does not change

The CLI keeps a blocking confirm by passing a policy that resolves inline; the
MCP server and eval harness are unaffected in behaviour. The `<tool_data>`
framing, the tier system and the injection defences are untouched.

## 8. Data lifecycle and privacy

- **Synthetic by default.** Every visitor's ledger is a lazy clone of the 352-row
  seed corpus, materialised on their **first request that actually needs a
  ledger** — the first chat message, or the first view of `/dashboard`, whichever
  comes first — rather than on page load, so crawlers and bounces cost nothing.
  A single `ensureLedger(ownerId)` call guards both entry points and is a no-op
  once the ledger exists. ~140 KB per visitor, and the insert is one batch of 352
  transactions plus 704 postings.
- **Uploads.** Anyone, including anonymous visitors, may import a CSV. The raw
  file is **never written to disk or to the database** — it is parsed in memory
  and only derived rows are stored.
- **Anonymous retention is 24 hours**, stated plainly in the UI at the point of
  upload, enforced by a nightly reaper, and cleared by signing in.
- **Deletion.** `/settings` offers one-click deletion of the entire ledger and
  of the account, cascading through `owner_id`.
- **Privacy page** states what is stored, for how long, that the site is a
  demonstration rather than a financial service, and that the operator can view
  diagnostic traces which include ledger contents (§9.5).
- `data/private/` stays gitignored; no real statement data ever enters git.

## 9. Admin dashboard

The owner needs one place to see what the deployed app is actually doing —
above all what it is costing, because the $20 ceiling in §5 is the binding
constraint and a surprise there is a surprise on a personal card.

### 9.1 Authorization

Access is by session email against an `ADMIN_EMAILS` allowlist (comma-separated
env var). No roles table: there is exactly one operator, and a table would be
ceremony around a constant.

Unauthorized requests get **404, not 403**. A 403 confirms the route exists,
which is free reconnaissance for anyone probing a public site.

### 9.2 The RLS bypass has exactly one door

This is the security-critical part. The admin dashboard must read across every
owner, which is precisely what §4.2 exists to prevent. Two rules:

1. All admin reads go through `packages/ledger/src/repo/admin.ts` and nowhere
   else. That module is the only place in the application permitted to use the
   RLS-bypassing role, and every function in it takes an already-verified admin
   session rather than re-checking authorization itself.
2. Every function in that module is read-only except the two operator actions in
   §9.4, which are individually named and audited.

A reviewer should be able to answer "how could one user see another's data?" by
reading one file.

### 9.3 What it shows

Seven panels at `/admin`, each drilling into the existing trace viewer.

1. **Budget** — spend today against the daily cap, month-to-date against the
   monthly ceiling, projected month-end at the current burn rate, a 30-day
   sparkline, and whether the kill-switch is armed or tripped. First and largest,
   because it is the number that can hurt.
2. **Traffic** — visitors today / 7d / 30d, anonymous versus signed-in, the
   anonymous-to-account conversion rate, new versus returning.
3. **Health** — run status split (`ok` / `error` / `blocked` / `aborted`), p50 and
   p95 latency, iteration-limit hits, and tool error rate.
4. **Safety** — writes proposed, allowed and declined; uploads processed;
   `blocked` runs with their provider reason. These are the guardrails' field
   results as opposed to their eval results.
5. **Tools** — per tool: call count, error rate, median latency. Sortable. This is
   how you learn which tool descriptions are failing to earn selection.
6. **Recent runs** — the existing `/runs` table widened with an owner column and
   unscoped, linking to `/runs/[id]`.
7. **Users** — created, kind, messages used today, cost attributed to date, last
   seen, blocked state. Cost per user is how abuse becomes visible.

All of it is derived from `trace_runs`, `trace_events` and the Better Auth `user`
table, which already record everything listed. No new instrumentation is
required, and deliberately **no rollup tables**: at ~148 turns/day a direct scan
stays fast for years, and a rollup is a cache to invalidate for no present gain.

### 9.4 Operator actions

Two writes, because a read-only dashboard cannot stop an incident:

- **Pause live chat** — a manual kill-switch independent of the budget trip, so
  the site can be put into replay-only mode instantly.
- **Block an owner** — `user.blocked_at`; blocked owners get the same graceful
  fallback as a quota trip rather than an error.

Both are logged to `trace_events` with `type = 'error'` and an explicit
`kind: 'operator_action'` payload, so operator interventions appear in the same
timeline as everything else rather than in a separate place nobody reads.

### 9.5 Privacy consequence

Trace payloads contain tool arguments and results, which for this app means
transaction descriptions and amounts. An operator viewing a trace is therefore
viewing that visitor's ledger contents. That is the honest meaning of "see
everything that happened", and the privacy page must say so plainly rather than
leaving it implied. It is a small exposure here because ledgers are synthetic by
default, but it is not zero once a visitor uploads a real statement.

## 10. Environments and deployment

- **Vercel** for the app, **Neon** for Postgres.
- **The production database must be unreachable from `pnpm eval`**, which
  truncates and reseeds before every task. Two mechanisms: production
  credentials never present in a local `.env`, and a guard in `resetAndSeed()`
  that refuses to run unless the `DATABASE_URL` host is localhost or
  `ALLOW_DESTRUCTIVE_RESET=1` is set explicitly.
- Secrets live in Vercel environment variables. `.env.example` gains the new
  keys with empty values.
- New env: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`,
  `GOOGLE_CLIENT_SECRET`, `TURNSTILE_SECRET_KEY`,
  `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, `GLOBAL_DAILY_BUDGET_USD`,
  `ANON_DAILY_MESSAGE_QUOTA`, `USER_DAILY_MESSAGE_QUOTA`, `RATE_LIMIT_SALT`,
  `ALLOW_DESTRUCTIVE_RESET`, `ADMIN_EMAILS`.

## 12. Out of scope

Bring-your-own-key. Paid tiers. Live bank connections. Real FX. Mobile app.
Voice mode. Multi-provider adapters. Team or shared ledgers. Anything that turns
this into a financial service rather than a demonstration of one.
